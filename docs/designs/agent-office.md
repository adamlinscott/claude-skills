# Design: Agent Office, a reverse-harness pane for Claude Code

## Problem Statement

claude-skills now ships Role agents (scout, researcher, worker, worker-light, reviewer), and
the long-term goal is a team of specialist agents (UX, security, testing, critics) whose work
combines into detailed specs and builds that are aware of other work going on around them.
Today none of that activity is visible. A developer working across several sessions and Orca
worktrees of one repo can't see which sessions are live, which agents they have spawned, what
each agent is doing, or where two pieces of work are about to collide. Without that view, any
agent-to-agent network built later can't be checked, understood or tuned.

> "The network is the wow moment. However, there's no way to actually verify and understand
> and use that network effectively without having the view first."

## What Makes This Cool

It is a **reverse harness**. A normal harness sits outside one agent and controls it. This
pane sits inside one session and looks out over the rest of the company: your room in the
centre, the other sessions of the same git project around it, their agents at desks placed by
job type, and lines wherever two sessions are touching the same files. The view comes first,
but v1 already shows part of the network, inferred read-only from the session logs, with no
agent having to send a message.

## Constraints

- It is a Claude Code mod pane. Panes draw an element tree (Box, Text, Button, Image, Raster).
  Svg works only in the Desktop app, and HTML is not supported. Refreshes come from
  `$.clock.every` or `$.ui.invalidate`.
- No shared folder and no "run from the root" requirement. Discovery must be automatic.
  Projects and worktrees live anywhere on disk (Orca worktrees sit under
  `~/orca/workspaces/...`, and the main checkout sits under `~/Projects/...`).
- The default scope is the current git project, including all its local worktrees. Other
  projects are a nice-to-have, not part of v1.
- No server, no hook installation, and no SSH or special CLI flags. Setups must be
  self-contained.
- Anything a person tunes (the zone layout, recency windows) lives in a plain, clearly labelled
  file, never hardcoded.
- It installs through claude-skills' `install.mjs` like skills and agents do. It is on by
  default for developers only.

## Premises (agreed)

1. **Visual from v1, not pixel art.** (Revised after the session.) v1 draws the office as a
   floor plan: rooms, desks placed by zone, status shown as colour, started-by lines and
   same-file lines. Status words and text lists are not the interface. Claude Desktop is the
   primary target (`Svg` vector plan in the side panel). The terminal (Orca today) gets the same
   plan drawn with `Raster` coloured cells. The bar: a better multi-agent overview than Orca
   gives, good enough to move day-to-day work into Claude Desktop. Pixel characters stay out of
   scope.
2. **Discovery reads the transcripts Claude Code already writes**, grouped by
   `git rev-parse --git-common-dir`. The format is internal, so all parsing lives in one
   module, and a format change is a one-file fix.
3. **The proof of concept is read-only.** The pane never sends messages and never spawns or
   steers agents. Messaging is v2.
4. **Placement comes from agent type** through an editable `zones` file, never hardcoded.

## Landscape

Pixel offices: Claude Office Visualizer (boss and employee subagents, run through hooks, a
FastAPI server and a web UI), Pixel Agents (a VS Code extension), pixelagents (served on
localhost), pixtuoid (a terminal version). Observability: agents-observe, disler's
hooks-multi-agent-observability, agentsview, and Agent Tmux Monitor. Going by their published
descriptions (their source has not been read), all of them need a server, a web UI or both,
and most also install hooks. None describes grouping sessions by git project and its worktrees,
placing agents by kind of job, or inferring links between sessions. Confirm this during the
Pixel Agents source read.

## Cross-Model Perspective (Claude subagent, cold read)

- **Coolest version:** infer the network from transcripts. Edit, Write and Read calls name file
  paths, so when sessions in different worktrees touch the same file, draw a line and pin a
  card to the board. That gives pre-merge conflict warnings and a dependency map in v1. Later,
  clicking a line could send a message to either session.
- **What excites the user:** "The network is the wow moment." The PoC should include part of
  the network, or it will feel like a chore.
- **Halfway there:** Pixel Agents may parse JSONL transcripts directly. This is unverified;
  read its parser before writing ours, but don't fork it, because it is tied to VS Code.
- **Build order:** a discover CLI first, tested against real worktrees, then a Box/Text pane.
  Art comes last.

## Recommended Approach: B, built in A's order

One **discover module** builds an **office snapshot**. Three things consume it.

```
transcripts (~/.claude/projects)        zones.json
          │                                 │
          ▼                                 ▼
   discover module ──► office snapshot (JSON) ◄── git --git-common-dir cache
          │                 │                 │
          ▼                 ▼                 ▼
     mod pane         collisions/board    /office skill (agent reads it, v1.5)
   (you are here)     (inferred links)    → v2: SendMessage on a link
```

**Office snapshot (sketch):**
```json
{
  "project": "C:/Users/adamr/Projects/claude-skills/.git",
  "self": "a4b66df9-…",
  "sessions": [{
    "id": "a4b66df9-…", "branch": "adamlinscott/paddlefish", "cwd": "…/paddlefish",
    "lastActive": "2026-10-09T16:58:00Z", "status": "active|idle",
    "agents": [{"id": "a0b3…", "type": "researcher", "zone": "library",
                "lastTool": "WebFetch", "lastFile": null, "age_s": 12, "status": "running|done"}],
    "filesTouched": ["install.mjs", "agents.txt"]
  }],
  "links": [{"a": "a4b66df9-…", "b": "bb31c5c4-…", "kind": "same-file", "files": ["install.mjs"]}],
  "board": [{"from": "reviewer@a4b66df9", "kind": "finding|collision", "text": "…", "at": "…"}]
}
```

**Data wireframe (superseded as the UI by the visual floor plan; see Premise 1 and the presentation page):**
```
┌ claude-skills ── 3 sessions, 3 agents ─────────────────┐
│ ★ YOU  adamlinscott/paddlefish                 active  │
│   library   researcher  WebFetch          12s          │
│   archive   scout       Grep agents/      40s  done    │
│                                                        │
│   main                                         idle 4m │
│   adamlinscott/sunfish                         active  │
│   workshop  worker      Edit install.mjs   3s          │
│                                                        │
│ ⚠ COLLISIONS                                           │
│   sunfish ↔ YOU: install.mjs                           │
│ BOARD                                                  │
│   reviewer@main: "stale comment in skills.txt parser"  │
└────────────────────────────────────────────────────────┘
```
Your room is always first. Other rooms are ordered by relevance: a shared-file link first,
then most recently active. Zones come from `zones.json`, for example
`{"scout":"archive","researcher":"library","worker":"workshop","worker-light":"workshop","reviewer":"review room","*":"open floor"}`.
An agent whose type can't be read sits in the `*` zone, labelled `?`.

### Discover module rules

- **Self.** The pane passes its own session id to the discover module, taken from the mod API's
  session context if the sandbox probe finds one there. The CLI takes `--self <id>`. With no
  id (from either the CLI or the pane), the module marks the most recently written transcript
  whose `cwd` matches the current directory, and shows it without the ★ if that is ambiguous.
- **Liveness** (in the tunable config): a session's last-active time is the newest mtime
  across its own transcript and its `subagents/` files. `active` means within 2 minutes,
  `idle` means within 30 minutes, and anything older is hidden. A session that is open but
  quiet for more than 30 minutes is hidden on purpose; the success criteria assume active
  sessions.
- **Agent done.** For a foreground spawn, the parent transcript holds a `tool_result` for the
  Agent tool_use. For a background spawn, that `tool_result` is only a launch acknowledgement
  and does not count. Done then needs the completion notification in the parent, or the
  quiet-file rule: the subagent's last line is an assistant message with no pending tool_use,
  and the file has been quiet for at least 60 seconds. Milestone 1's probe covers both a
  foreground and a background spawn.
- **Touched files.** A session's touched files are the union of its own transcript and all its
  subagent transcripts. Only Edit, Write and NotebookEdit targets count; Read is excluded
  because it is too noisy. Only touches from the last 30 minutes count (tunable). Each path is
  made relative to `git rev-parse --show-toplevel` for the cwd of whichever transcript made the
  call, with forward slashes, and lower-cased on Windows. Paths outside the worktree are
  ignored. Collisions are the intersection of these relative paths.
- **Board.** Each card is the final assistant message from a subagent JSONL whose type is in
  the config's `boardAgents` list (default `["reviewer"]`; /fresh-eyes runs the reviewer
  agent), read by the discover module for every session, not through hooks. Cards come only
  from sessions currently shown, newest first, capped at a tunable count (default 5), and drop
  when their session is hidden. Collisions get their own COLLISIONS section and do not appear
  on the board. Card text is truncated to the card width.
- **Cost.** Filter transcripts by mtime first, then read each one incrementally from a cached
  byte offset. A pane refresh renders the last snapshot and never waits for a full rescan.
- **Degraded mode.** Skip unparseable lines. Skip any cwd that git can't resolve, such as a
  removed worktree. If git is missing, or no line parses at all, the pane shows a one-line
  status ("transcript format not recognised" or "git not found") and no empty office.

### LLM budget: deterministic first, cheap model only for meaning

> **Revised after the session:** room summaries come from the session's own data, else the cheapest Claude model via `$.model.complete` on the person's billing (no key). Decision models (JEV, Perplexity Decisions) are only for categorising and fuzzy relatedness with confidence, never for writing text; the beta installer offers JEV, Perplexity Decisions or None, with keys in user environment variables. Which checks they run is open on map #41.

Most of the snapshot comes straight from the transcripts with no model involved: sessions,
branches, agent types, tool names, file paths, timestamps, collisions and statuses. An LLM is
used only where the logs hold no field for the answer and the answer needs judgement about
meaning:

| Need | Source |
|---|---|
| Which sessions, branches, agents, tools, files, ages | Parsed from transcripts (no LLM) |
| Collisions | Set intersection of files touched (no LLM) |
| Board text for reviewer output | Final assistant message in the subagent JSONL, truncated (no LLM) |
| "What is this room working on" (a one-line label per session) | Cheap model, from branch, touched file paths and agent types |
| Condensing a long finding into a card title | Cheap model, only when the verbatim text exceeds the card width |

Rules: use JEV (TypeSafe AI's "System One" model), the cheap model chosen for this kind of data-filling, with a Haiku-class model as the fallback. Cache every result
by session id plus transcript byte offset, so a room is relabelled only after it changes
materially, never once per refresh. If no model is available, the pane still works and falls
back to branch names and truncated text. The pane never needs the LLM in order to draw.

This is **post-v1 (milestone 3.5)**. Milestones 1-3 ship with no model calls at all. The
mechanism is still open: JEV through its API, with the key read from the user's existing JEV setup, never stored in this repo. The fallback is a mods API for model calls, if one exists, or `claude -p
--model haiku` through `$.process` on the user's existing Claude login. Either way there is no
new key and no server. Data handling: a label prompt contains only the branch, touched file
paths and agent types, never user-turn text, so pasted secrets don't flow into labels. Board
text is shown locally, to the same user, from their own transcripts.

### Milestones

1. **Probes, then discover module + CLI** (`node discover.mjs --json [--self id]`).
   - Transcript probe: find where agent type, tool names, file paths and done markers live.
   - Mod sandbox probe: test whether `$.fs` can read `~/.claude/projects`, whether
     `$.process` can run `git` and `node`, whether the mod API exposes the current session
     id, and what a `Client` drawing area can run (needed for clicks in v3). Plan for each outcome:
     - Both work: run the module in-process.
     - `$.process` only: run `discover.mjs` through `$.process` and parse its JSON.
     - `$.fs` only: resolve the common dir and toplevel by reading the worktree's `.git`
       file, its `gitdir` pointer and `commondir`, with no git binary.
     - Neither works: stop and rethink the pane approach before milestone 2. The CLI and the
       `/office` skill still stand.
   - Then build the module to the rules above and test it against real Orca worktrees.
2. **Floor-plan pane + installer.** One layout model drawn two ways: `Svg` in Claude Desktop
   and `Raster` cells in the terminal, refreshed every few seconds. Rooms, desks by zone, status
   by colour, started-by lines, and "you are here". Add mod support to `install.mjs` and a manifest
   entry, linking to the documented mods install location (confirm it from the plugin-authoring
   docs). `zones.json` and the config ship as repo defaults. Users override them in
   `~/.claude/agent-office/zones.json` and `config.json`, merged per key on top of the repo
   default, so new defaults (such as a new Role agent type) still apply after `git pull`.
3. **Collisions and board.** Add file-overlap links between sessions to the snapshot and pane,
   and add board cards (see Discover module rules).
3.5. **Cheap-model room labels** (see LLM budget). Success means each active room shows a
   one-line label that refreshes only after material change.
4. **`/office` skill (v1.5).** It hands the same snapshot to the agent in this session, so the
   agent can check before editing a file that another session is already changing.
5. **v2 (out of scope here):** send a message along a link through the cross-session
   SendMessage, and specialist agents that subscribe to board cards.
6. **v3, the playable office (future vision, out of scope).** This is a Sims-like layer where you
   select a subagent and take control of it: inject context into it, steer it, or act on its
   behalf, then watch the other agents react. It turns the office from something you watch into
   something you play, and it changes how agents interact: the human becomes one more
   participant in the network, not only the one giving orders. It builds on v2's links and on
   the snapshot, and needs its own design pass on consent, interruption rules and
   reversibility.

## Success Criteria

- With three sessions open across two Orca worktrees and the main checkout of claude-skills, the
  pane in any one of them lists all three, with correct branches, within one refresh, with
  nothing configured.
- A scout or researcher spawned in another session appears at the right zone's desk while it
  runs, and is marked done after it stops (in the foreground or the background). This requires
  the milestone-1 probe to find agent type in the transcripts. If it doesn't, other sessions'
  agents show on the open floor as `?`, and correct zone placement is required for this
  session's agents only.
- Editing the same file from two worktrees produces a collision line within one refresh.
- A Claude Code update that changes the transcript format breaks only the discover module, and
  the pane shows a one-line status rather than crashing.
- Milestones 1-3 make no model calls.

## Distribution Plan

The mod lives in this repo next to `skills/` and `agents/`. `install.mjs` currently has no mod
support, so milestone 2 adds it: a manifest entry, and linking into the mods install location.
It is on by default for developers and off for the non-technical setup. `zones.json` and the
config ship as repo defaults, with per-key user overrides in `~/.claude/agent-office/`. There is
no CI beyond the existing flow, and teammates get updates with `git pull`.

## Reviewer Concerns

### R2-1 — consistency

**Problem**

> The LLM budget table says the room label comes 'from the first user turn plus recent tool targets', but the data-handling rule below it says a label prompt contains only the branch, touched file paths and agent types, 'never user-turn text'. The two statements contradict each other on exactly the point the data-handling rule exists to settle.

**Remedy**

> Change the table row's source to 'branch, touched file paths and agent types' so it matches the data-handling rule.

### R2-2 — feasibility

**Problem**

> The 'Agent done' primary rule treats a tool_result for the spawning Agent tool_use as done. Background subagents (run_in_background, which is the default in some setups) get an immediate tool_result acknowledging the launch, so this rule would mark a still-running scout or researcher as done, breaking the 'marked done after it stops' success criterion.

**Remedy**

> Make the milestone-1 probe check a background spawn, and specify that a launch acknowledgement does not count as done (for example, require the completion notification or fall back to the quiet-file rule for background agents).

### R2-3 — completeness

**Problem**

> Liveness is defined by when 'the transcript' was written. While a session waits on a long-running subagent, only the subagent JSONL is being written, so the parent session can show idle, or be hidden after 30 minutes, while its agent is visibly working.

**Remedy**

> State that a session's last-active time is the newest mtime across its own transcript and its subagents/ files.

### R2-4 — clarity

**Problem**

> The 'Touched files' rule doesn't say whether Edit/Write calls made inside a session's subagent transcripts count toward that session's filesTouched. The wireframe's collision (a worker in sunfish editing install.mjs) depends on subagent edits counting.

**Remedy**

> State that filesTouched is the union of the parent transcript and all its subagent transcripts, using the subagent's cwd/worktree for path normalisation.

### R2-5 — feasibility

**Problem**

> The mod sandbox probe defines only the case where neither $.fs nor $.process works. If $.fs works but $.process does not, the pane can read transcripts but cannot run `git rev-parse --git-common-dir` or `--show-toplevel`, which project grouping and path normalisation both require. If $.process works but $.fs does not, the shell-out-to-discover.mjs path is no longer stated anywhere.

**Remedy**

> State the plan for each partial outcome: fs-only (e.g. resolve the common dir by reading the worktree's .git file and gitdir pointers, or stop), and process-only (run discover.mjs via $.process and parse its JSON).
