# How the installer lists the skills.
#
# One line per checkbox:
#
#   <name> | <folders> | <what it does> | <dev>,<nontech>
#
#   name         what the installer shows, and what beta-features.txt refers to.
#   folders      comma-separated folder names under ./skills that this entry installs.
#                Several folders can share one checkbox — an alias like /seatbelts or
#                /to-the-point is another way to invoke the same skill, not another choice.
#   description  written for the PERSON INSTALLING, not for Claude. The description inside a
#                SKILL.md is written to help Claude decide when to use the skill; it is long and
#                technical and makes a poor answer to "what is this?". Write a plain sentence or
#                two here instead.
#   defaults     on/off for each of the two setups the installer offers:
#                  dev      "Let me choose" — is this ticked when the checklist opens?
#                  nontech  "Set it up for me" — is this installed with no question asked?
#                Leave the column off entirely and you get `on,off`, which is what almost
#                everything here wants: available to a developer, not part of the guided setup.
#                Anything unparseable resolves to OFF, never on — a typo must never quietly
#                install something on someone's machine.
#
# A track default can only ever ADD. Neither setup removes a skill you already have; only a
# checklist you actually saw can do that.
#
# WHEN DOES A SKILL EARN nontech:on?
# Two ways, and the second is easy to forget:
#
#   1. They can reach for it themselves. They can tell when it is needed and can read what it
#      gives back. /raise-issue is the clearest case — "something is broken" is a judgement
#      anyone can make about a product they use.
#   2. Someone else can refer them to it. They do not have to know it exists. They say "Claude
#      has been odd lately", a technical colleague says "run /memory-audit", and it has to
#      already be installed for that sentence to work. This is why /memory-audit is on the list
#      despite a non-technical user never thinking to run it unprompted.
#
# A referral has to survive a round trip to another human, so route 2 only works for a problem
# that WAITS — stale memory, a bad setting, machine state. It does not work for anything that
# has to be caught live: by the time they have asked you, that session is gone. /reground is
# exactly that case, which is why it is on,off rather than on,on despite being genuinely useful.
#
# And whatever the route, check what the skill PRINTS. A report of file:line citations is no use
# to someone who does not read code, however correct the diagnosis.
#
# RETIRING A SKILL
# Set its defaults to `off,off`, start its description here with "DEPRECATED — use /x instead",
# and add a line for it to deprecated.txt. That last file is what makes the installer label it on
# the checklist and offer, once, to remove it from a machine that still has it. Do not delete the
# folder: a removed skill leaves anyone who installed it holding a command that silently stopped
# existing. See deprecated.txt for the whole reasoning.
#
# A folder with no line here still installs, on its own, with no description. Blank lines and
# lines starting with # are ignored. The installer reads this at run time.

are-we-done | are-we-done | Checks whether a session can actually close: sweeps the todo list, the loose ends in the conversation, the state of your files, and any issue numbers mentioned, then tells you either "yes, done" in one line or exactly what is still undecided. Changes nothing. | on,off

assumption-inventory | assumption-inventory | DEPRECATED — use /build-it instead. Before a long job, checked what the plan took for granted — which files exist, what may be changed, what "finished" means — and asked you about anything it had to guess. /build-it now does the same work as part of pinning scope, so running both filled the same form twice. Kept only so existing installs point somewhere. | off,off

brief-me | brief-me | Catches you up on a session you have lost the thread of — after a distraction, or over a weekend. Explains in plain English what you were doing, where it got to, what state it is in now, and what it is waiting on from you. Changes nothing. | on,on

build-it | build-it | Builds a piece of work from wherever it is written down — a ticket number, a plan file, the plan you just agreed in the conversation, or a description typed straight after the command. No issue tracker needed. It reads the source and the code it points at, asks you whatever neither of those answered — the why, above all — then writes down exactly which files it will change and which it will not, and builds to that. If the job turns out to be big and still vague, it says so and suggests planning it properly first. | on,off

check-skill-updates | check-skill-updates | Checks whether the skills on your machine are behind the copy they were installed from, and offers to bring them up to date. Mentions it at most once a day, only when you are between tasks, and never again once you have said no to a version. | on,on

context-audit | context-audit | Reviews the instructions and notes Claude reads in a project, and reports what is bloated, broken, or contradicting itself. Only reports; changes nothing. | on,off

debrief | debrief | Reads back through your past Claude sessions to find the corrections you keep repeating, asks you why, and can write the answers up as project rules. | off,off

fresh-eyes | fresh-eyes | Gets a second Claude to read your finished work with no memory of the conversation, then compares that reading against what you actually asked for. Catches what was missed. | on,off

goal-workflow | goal-workflow | DEPRECATED — use /build-it instead. Handed Claude a settled plan and let it build the whole thing on its own. It forced maximum effort, always split the work across sub-agents, and re-checked itself at every step — all of which current Claude models either do on their own or are actively slowed down by, which is why it stopped performing well. Kept only so existing installs point somewhere. | off,off

memory-audit | memory-audit | Tells you what Claude remembers about a project and whether any of it has gone stale. Only reports; changes nothing. | on,on

raise-issue | raise-issue, report-issue | Turns "the export button is broken" into a proper issue on your team's tracker. Asks a few plain questions, works out which part of the code you mean, checks nobody has reported it already, and shows you the finished issue before it files anything. | off,on

reground | reground | Stops Claude when it has wandered off the task or started inventing files and APIs, and pins it back to what is really in your code. | on,off

seatbelt | seatbelt, seatbelts | Decides up front what Claude may do in a project without asking, and what it must never do. Set it once, then let Claude run without watching every step. | off,off

ship-it | ship-it | Takes the work from a finished session all the way out — merges it, releases it, and checks each environment is really running it, production last. If the release would carry other people's unreleased work along with it, it tells you whose and asks before touching production. Developer setups only. | on,off

ship-it-now | ship-it-now | The same as /ship-it, but it does not stop to ask before deploying other people's unreleased work — it names whose work is going out and carries straight on to production. Needs /ship-it installed alongside it. Developer setups only. | on,off

ttp | ttp, to-the-point | Makes Claude's replies short and direct — the answer first, the detail only if you ask for it. Big decisions still come back to you. | on,on
